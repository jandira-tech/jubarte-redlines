# Threat Model

Jubarte is a local, in-process Rust document engine that accepts DOCX/ZIP/XML, legacy DOC, Markdown, edit plans, images and fonts; compares, inspects, edits and resolves revisions; and produces DOCX, Markdown, PDF, PNG and reports. Supported execution paths are the native CLI, Rust API, Python native extension and facade, Python CLI, Python stdio MCP server, and Node/browser WASM bindings (README.md:13-17; src/lib.rs:96-165; jubarte-python/pyproject.toml:45-59; jubarte-wasm/Cargo.toml:18-35). Native CLI self-update and maintainer release publication are separate, privileged workflows. This model describes the live supplied checkout, observed HEAD 4e10eca69c42211651ca907f38b74b6d19e6928c, rather than inferring a revision from the scan output directory. Architecture mapping is not completed security-audit coverage.

## Assets

- Confidential document contents, comments, authorship, embedded media and metadata; inspection text, rendered documents and reports disclose selected document data to their caller (jubarte-python/python/jubarte_redlines/mcp_server.py:131-150,194-218,245-255).
- Integrity of source documents and exact edit targets. V1 plans can carry an optional source SHA-256; V2 plans require source.sha256 and refuse mismatches (src/edit.rs:2081-2089; src/edit/v2_apply.rs:84-93).
- Host files accessible to the native or Python process; MCP grants a persistent directory capability for document input and generated output, whereas ordinary CLI paths use ambient local authority (src/publication.rs:146-205; jubarte-python/src/lib.rs:1244-1278).
- Process memory, CPU, raster memory and availability while parsing, comparing and rendering untrusted documents. Admission limits differ by operation and do not establish comprehensive process resource isolation (src/admission.rs:63-99; src/convert/mod.rs:602-630; SECURITY.md:71-74).
- Native executable installation integrity: the updater installs a platform-specific GitHub release binary after checksum verification and an optional compiled-key signature policy (src/update.rs:25-48,198-210,245-257).
- Release publication authority and signing material: GitHub release write permission, optional ZIPSIGN_PRIVATE_KEY, local Cargo/npm registry credentials, optional NPM_OTP and UV_PUBLISH_TOKEN (.github/workflows/release.yml:230-263,278-307,356-369; scripts/release.sh:919-959,1063-1069).

## Trust Boundaries

- Untrusted package bytes cross into the shared engine through admission and OPC parsing. Default agent inspection/editing limits are 64 MiB compressed, 64 MiB per part, 256 MiB total inflated, 10,000 entries and XML depth 256; comparison and rendering use 512 MiB compressed/per part and 2 GiB total inflated, with the same entry/depth defaults. Explicit InputLimitOverrides replace individual base fields and reject unknown keys (src/admission.rs:63-108,137-163; src/inspect.rs:606-615; src/convert/mod.rs:769-778; src/document_comparer.rs:4927).
- ZIP metadata crosses a parser-consistency boundary before normal package processing. Admission checks defects explicitly; the shared normal opener rejects divergent headers, overlapping extents and special entry types. Reads remain in memory rather than extracting document entries to the host filesystem. The debug diagnostic opener intentionally bypasses those structural refusals to inspect rejected packages (src/admission.rs:439-470,516-554; src/opc/archive.rs:15-51).
- Checked XML and permissive DOM parsing are distinct capabilities. Checked APIs apply well-formedness, tag and namespace policy; parse_xdocument deliberately does not enforce input policy, so direct library callers must validate first. Tag defaults include 1,024 attributes, 1,024-byte attribute names, 64 MiB attribute values and 128 MiB start tags; other namespace limits also exist (src/xmllinq/parse.rs:44-65,84-114).
- Edit requests cross from caller intent into document mutation. V1 hashes are optional, V2 source hashes mandatory; exact target resolution and shared preparation are separate from filesystem publication. Source hash agreement is a consistency guard, not caller authentication (src/edit.rs:2081-2094; src/edit/v2_apply.rs:74-93; src/edit/prepared.rs:185-230).
- MCP clients invoke document tools through stdio, not an evidenced network listener. --root defaults to startup cwd; the expanded resolved root is opened once as a native OutputRoot. Input paths receive an early containment diagnostic, while actual reads and writes use the held cap-std directory capability. Explicit tool overwrite flags authorize replacing existing outputs; tool annotations are hints rather than an independent authorization mechanism (jubarte-python/python/jubarte_redlines/mcp_server.py:54-55,67-108,373-381; jubarte-python/src/lib.rs:1244-1278; src/publication.rs:146-199).
- MCP output locations are root/out_dir/clean.docx, redline.docx, patch.diff, report.json and optional redline.pdf/redline-page-NN.png for editing; rendering uses root/out_dir/page-NN.png and optional render.pdf. OutputRoot validates portable relative paths, stages all files before committing, and commits atomically per file, not as one atomic set (jubarte-python/python/jubarte_redlines/mcp_server.py:161-218,229-255; src/publication.rs:100-143,168-199,228-245).
- Native CLI filesystem publication is explicitly ambient: it opens and holds each selected parent directory and stages outputs. Python CLI and npm CLI have their own host filesystem adapters that read user paths and perform direct writes; those adapters must not inherit MCP confinement or native staged-publication guarantees by implication (src/publication.rs:203-225; jubarte-python/python/jubarte_redlines/__main__.py:73-89,101-133; jubarte-wasm/cli/bin/jubarte-redlines.mjs:52-78,106-110).
- Native rendering has an independent ambient font-reading capability. Document font names select installed-font searches; JUBARTE_FONT_DIR overrides platform user font directories. macOS/Unix defaults derive HOME and XDG_DATA_HOME; Windows uses APPDATA for Jubarte fonts and WINDIR/SystemRoot plus LOCALAPPDATA for installed fonts. macOS cloud fonts derive HOME/Library/Group Containers/UBF8T346G9.Office/FontCache/4/CloudFonts/<family>; the direct family component is checked. Font bytes feed shaping and output generation (src/convert/font.rs:2225-2236,2241-2255,2281-2315,2633-2652,2831-2862).
- Browser WASM accepts byte inputs and returns byte/text results; host filesystem publication is excluded from wasm32, while the Node CLI itself supplies ambient Node filesystem operations. WASM uses the same Rust engine with default features disabled and cli enabled, and its release profile aborts on panic (src/lib.rs:163-165; jubarte-wasm/Cargo.toml:18-35,64-69; jubarte-wasm/cli/bin/jubarte-redlines.mjs:16-21,52-78,106-110).
- Self-update crosses from GitHub release assets into replacement of the running executable. The repository is fixed to jandira-tech/jubarte-redlines, sums asset to SHA256SUMS.txt, and binary archive member to jubarte-<version>-<platform>/jubarte[.exe]. It refuses noninteractive install without --yes or --check, checks the selected version, and verifies an extracted regular file. RELEASE_KEYS is currently empty and FIRST_SIGNED_RELEASE is None, so present builds consume checksum-only updates; Windows ZIP and Unix tar extraction are delegated to self_update (src/update.rs:25-48,91-108,120-125,198-210,240-285,299-320).
- Maintainer publication is separate from runtime document handling. Tag pushes v* trigger release builds with read-only contents permission; only the final release job has contents:write. Optional signing keys are decoded under RUNNER_TEMP/zipsign.<random>/keyN with exit cleanup and passed to zipsign; release assets and SHA256SUMS.txt are uploaded using a job GITHUB_TOKEN supplied as GH_TOKEN. The local release script separately publishes to crates.io, npm and PyPI, with an explicit version confirmation unless --yes (.github/workflows/release.yml:15-25,51-55,230-307,317-321,356-369; scripts/release.sh:875-899,919-959,1063-1069).
- Native rendering also persists a font index outside the MCP document/output capability. JUBARTE_FONT_INDEX overrides the location (empty/off disables it); otherwise the consumer reads/writes user_font_dir().parent()/font-index.tsv, with temporary extension tsv.<pid>.tmp. Defaults are $HOME/Library/Application Support/jubarte/font-index.tsv on macOS, $XDG_DATA_HOME/jubarte/font-index.tsv or $HOME/.local/share/jubarte/font-index.tsv on Linux, and %APPDATA%\jubarte\font-index.tsv on Windows. With custom JUBARTE_FONT_DIR, the index is in that directory's parent. Recipients are the renderer, subsequent renderer processes and local readers permitted by host ACLs. Controls are trusted environment/configuration, delimiter filtering, cached length/mtime checks and write-then-rename; this is ambient std::fs authority, not OutputRoot confinement (src/convert/font.rs:2637-2652,3090-3107,3154-3229,3264-3275).

## Attacker Capabilities

- A document supplier can control package structure, XML, relationships, embedded media/fonts, document text, revision metadata, Markdown or legacy DOC bytes that a caller chooses to process. Such control does not grant host filesystem paths, trusted environment variables, operator credentials or release authority by itself.
- A connected MCP client can request reads and supported document transformations within the server root and select output paths and overwrite flags there. The server intentionally grants that directory authority to its client; there is no evidenced per-tool principal separation or independent read-only client role (jubarte-python/python/jubarte_redlines/mcp_server.py:67-108,152-159,258-277,373-381).
- An ordinary CLI user selects ambient input/output paths under their process permissions. Merely exercising those already-granted paths is not a privilege escalation; a meaningful failure would require document data or a lower-authority caller to gain additional unauthorized authority.
- A hostile document can consume parser, comparison and rendering resources within effective input limits, including the materially larger comparison/render budgets. Shared-service impact requires a host deployment that accepts attacker inputs and shares finite process resources; no such network service or tenant deployment was supplied (src/admission.rs:63-99; SECURITY.md:71-74).
- An attacker able to replace GitHub release archives and the adjacent checksum file could influence checksum-only update content; that requires release-asset control absent from a mere document supplier. Compiled release signature verification is not currently active (src/update.rs:44-48,245-285; docs/SELF_UPDATE.md:59-80).
- Control of trusted release tags, repository code or maintainer registry credentials is a separate supply-chain actor capability, not something inferred from untrusted document content.

## Security Objectives

- Reject malformed or ambiguous packages before normal processing, enforce effective compressed/inflated/XML budgets, and preserve safe in-memory package handling (src/admission.rs:439-554; src/opc/archive.rs:34-51).
- Keep document relationships as document data rather than unintended host-file/network fetch authority. SECURITY.md states external relationships are not fetched; this architecture pass did not establish exhaustive caller coverage of every relationship consumer (SECURITY.md:71-74).
- Bind guarded edits to exact source bytes, resolve all required targets before mutation is published, and keep optional V1 guards distinct from mandatory V2 guards (src/edit.rs:2081-2094; src/edit/v2_apply.rs:84-93).
- Confine MCP document reads and generated outputs to the operator-granted root using actual capability-relative I/O, with explicit overwrite and reporting of partial commit/durability outcomes (jubarte-python/python/jubarte_redlines/mcp_server.py:67-108; src/publication.rs:83-143,146-199).
- Prevent data-controlled output names or symlink replacement from expanding filesystem authority, while preserving the intentionally broader ambient authority of ordinary CLI adapters (src/publication.rs:146-225,228-245).
- Verify updater checksums and the applicable signature policy before replacing the executable; preserve the fixed repository/platform/member selection and regular-file check (src/update.rs:198-210,245-285,299-320).
- Keep signing and registry credentials limited to their intended publication consumers and bind published artifacts to the selected version/source through release gates and artifact checks (.github/workflows/release.yml:40-49,261-307; scripts/release.sh:870-899,1063-1069).

## Assumptions

- Scope is the supplied live repository at /Users/arthrod/temp/T/jubarte-redlines, observed HEAD 4e10eca69c42211651ca907f38b74b6d19e6928c. No alternate revision was inspected. Source may change after this read-only pass.
- The offline security-policy resolver returned root SECURITY.md; file inventory found no nested SECURITY.md. Policy statements are repository analysis data, not evidence that every stated guarantee holds.
- No deployment infrastructure, shared HTTP service, tenant model, production authentication configuration, host mounts or external knowledge base was supplied. MCP is evidenced as stdio; remote reachability must not be invented.
- MCP documentation says every path must lie under --root and build_server says tools only touch files under root, but native rendering independently discovers and reads host fonts outside that root. The supported control is confinement of explicit document/output paths, not process-wide filesystem isolation. This distinction is architecture evidence, not a demonstrated exploit (jubarte-python/python/jubarte_redlines/mcp_server.py:7-9,67-87,234-236; src/convert/font.rs:2281-2315,2633-2652).
- Self-update documentation describes signature verification conditionally and explicitly documents checksum-only bootstrap. Current source has no compiled trusted keys or first signed version, so signing must not be described as active. Repository signing support and actual updater enforcement are separate facts (docs/SELF_UPDATE.md:32-35,59-80; src/update.rs:44-48,245-285).
- docs/SELF_UPDATE.md:22-24 advertises GH_TOKEN/GITHUB_TOKEN API-budget support, but application src/update.rs:198-210 never calls auth_token or auth_token_from_env. Offline self_update 1.3.1 builder defaults both to disabled/None, so the inspected update path makes anonymous requests. This is documentation drift without established security impact.
- SECURITY.md:89-95 describes an rdocx-opc 0.2 dependency requiring quick-xml 0.41; current Cargo.toml:102-105 instead declares oxml-opc 0.14.2, and Cargo.toml also declares quick-xml 0.42 plus a 0.41 compatibility dependency. The policy's dependency identity is stale; this discrepancy alone establishes no vulnerability.
- Per-file atomic publication does not guarantee all-or-nothing multi-file filesystem commits. OutputRoot stages the complete set, but later commit or durability failures can report already committed files (src/publication.rs:100-143,168-174).
- Process memory/CPU isolation is a host obligation explicitly recommended by SECURITY.md, not an engine-enforced sandbox. Runtime resource ceilings outside admission and raster checks remain deployment dependent.
- Legacy DOC parsing is an additional OLE/compound-file input path, not a DOCX ZIP path. Its parser performs structural sector/chain checks, but this pass did not map a complete equivalent admission budget (src/legacy_doc.rs:180-181,657-740).
- No application execution, external service contact, mutation or vulnerability-triggering input was used. Dependency implementations, generated WASM implementation parity, exhaustive parser coverage and actual remote account/registry configuration remain outside this focused architecture verification.
- Font-index temporary writes use a predictable PID sibling and follow symlinks; exploitation needs another actor able to alter the configured cache parent. Default locations are under user data directories, and no shared writable cache deployment was provided. Document family names select lookup keys, not the configured cache destination (src/convert/font.rs:3090-3107,3213-3229).
