## The growth thesis

“Faster DOCX engine” is a technical claim. “Generate your document with the library you already use, get the PDF immediately, and review changes before sending” is a task people can adopt. Win the missing step in existing workflows first, then expand into semantic editing. Do not make new users abandon their template/generation stack to try Jubarte.

Three early audiences have distinct jobs:

| Audience | Trigger | Current friction to verify in interviews | First useful result | Retention event |
|---|---|---|---|---|
| Python app developer generating invoices, letters, reports | Needs a PDF alongside an existing DOCX | Office service deployment; temporary files; inconsistent fonts | PDF bytes from an existing `python-docx`/docxtpl output | Second production integration run on a later day |
| TypeScript app developer with npm `docx` | Needs browser/server PDF preview and download | Server conversion dependency and round-trip latency | Local PDF preview from the same generated bytes | Integration committed into an independently owned app |
| Agent/automation builder editing contracts/policies | Must return reviewable changes, not opaque rewritten files | Hand-written OOXML, lost formatting, unverifiable changes | Original + clean DOCX + redline + PDF + validation report | Second distinct document task without maintainer assistance |

These are hypotheses. The Python ecosystem has a concrete public example of confusion converting an in-memory Document to PDF, but a closed 2022 issue is evidence of a task, not evidence of present purchase intent or a person to contact. [python-docx issue #1054](https://github.com/python-openxml/python-docx/issues/1054)

The integrations are technically plausible: `python-docx` saves to a binary stream, and npm `docx` produces buffers/blobs. Use those documented serialization boundaries; do not reach into their private XML objects. [python-docx file-like objects](https://python-docx.readthedocs.io/en/stable/user/documents.html), [docx documentation](https://docx.js.org/)

## Familiar usage, available before semantic editing

Python recipe (existing 0.9.2 functions, no new public API required):

```python
from io import BytesIO
from pathlib import Path
from docx import Document
from jubarte_redlines import docx_to_pdf

letter = Document()
letter.add_heading("Delivery confirmation", level=1)
letter.add_paragraph("Your order has been dispatched.")
package = BytesIO()
letter.save(package)
pdf = docx_to_pdf(package.getvalue())
Path("delivery.pdf").write_bytes(pdf)
```

A docxtpl recipe uses exactly the same `.save(BytesIO())` boundary after the caller's template rendering; verify the installed version in an integration test, never mutate or introspect its private document tree. Expose an optional `render_filelike(document)` helper only if observation shows that the three-line bridge is a recurring obstacle. G01 can launch with a recipe rather than another dependency.

Node recipe (existing byte API, generated document is still useful as DOCX):

```javascript
import { Document, Packer, Paragraph } from "docx";
import { createRequire } from "node:module";
import { writeFile } from "node:fs/promises";
const require = createRequire(import.meta.url);
const { docxToPdf } = require("jubarte-wasm");

const document = new Document({
  sections: [{ children: [new Paragraph("Your order has been dispatched.")] }],
});
const bytes = await Packer.toBuffer(document);
const pdf = docxToPdf(bytes);
await writeFile("delivery.pdf", pdf);
```

Label the synchronous conversion clearly. Server concurrency and browser responsiveness use the worker milestone; adding `await` to a synchronous WASM call does not make it nonblocking.

## G03: a playground that is an acquisition product

Reference prototype: `patches/0007-local-playground.patch` creates `examples/playground/index.html`, `examples/playground/src/{main,worker}.js`, `style.css`, `package.json`, `vite.config.js` and README. It implements local selection/render/compare/cancel/download; the task below adds the sample-first flow and browser verification. Planned tests: `examples/playground/tests/playground.spec.ts`.

The first screen offers three buttons: **Render a DOCX**, **Compare two versions**, **Try a sample**. The sample runs without an email, account or file upload. Show a PDF preview and download buttons for the relevant artifacts, together with “Run this in Python” and “Run this in JavaScript” tabs containing the actual install command and code. The snippet uses package version and chosen options from the completed run. Browser processing stays local; loading code/fonts can still access the static host, so say “document contents stay in your browser,” not “no network request ever.”

Use File.arrayBuffer, owned Uint8Array copies, one initialized worker, bounded jobs and PDF Blob object URLs. Revoke old URLs on replacement/dispose. Disable submission while the queue is full, offer cancel, show recoverable errors, and allow retry after worker termination. Never send document bytes, names or extracted text to analytics/error tracking. An optional user-triggered “share a diagnostic receipt” exports a local JSON file first; sharing is a distinct choice.

Recommended instrumentation, only after opt-in: selected task, sample vs user-selected file, completion/error code, elapsed-time bucket, copy-snippet event, selected language. No fingerprint, cross-site identifier, filename, text, or persistent per-document hash. With no consent, aggregate deployment/server statistics can measure page delivery, but cannot establish successful conversions. Recruitment observers can record outcomes manually.

Acceptance: sample→PDF in a current Chromium and Firefox run, no document-content network request in captured request bodies, accessible keyboard/drop controls, all object URLs/workers disposed, supported byte limits enforced before large copies. Integrate `vite-plugin-console-pipe` for terminal/browser-console evidence as required by AGENTS.md. Static site publication remains a separate authorized action after review.

## G04/G11: make generated documents testable in CI

The useful unit is **template + representative data + expected output**, not a generic “convert all DOCX on every commit.” Propose a CLI recipe that renders candidate documents, compares accepted text/structure/page count with a checked-in baseline, and uploads an HTML/PDF/DOCX artifact bundle. Track template-generated fields separately only when the user names them; never ignore all dates, IDs or text globally.

Exact files: `examples/document-ci/fixtures/` (synthetic), `examples/document-ci/manifest.json`, `examples/document-ci/check.py`, `.github/workflows/document-example.yml`. The initial workflow triggers manually or on the example paths, has `contents: read`, and uploads artifacts. It does not require PR comment permissions or `pull_request_target`. Process untrusted documents without network access and with resource limits. Do not run contributor scripts from documents.

Proposed manifest contract:

```json
{
  "schema_version": 1,
  "engine": "jubarte-redlines",
  "cases": [
    {
      "id": "delivery-confirmation",
      "baseline": "fixtures/delivery-before.docx",
      "candidate": "fixtures/delivery-after.docx",
      "checks": {"page_count_delta_max": 0, "redline_required": true}
    }
  ]
}
```

Page count alone is not correctness. A configurable “expected change” in fixture text distinguishes deliberate wording updates from page-layout regressions. Produce a review artifact even when a gate fails, and link immutable engine/font versions. Keep Word fidelity evidence separate: a CI baseline is the project's baseline, not Microsoft Word's oracle.

## G05: review bundles and receipts as a shared interface

Proposed `ReviewBundle` contains `original.docx`, `edited.docx`, `redline.docx`, requested PDFs, `report.json` and an optional `index.html` local review page. The original is included only on explicit request; default artifacts refer to its hash, reducing accidental redisclosure. The receipt reports source/edited/redline SHA-256, engine commit/package version, options, font inventory/substitutions, policy checks, requested operation outcomes and validation levels achieved.

A receipt is evidence of a particular tool run, not a digital signature, legal approval, or proof that the text is legally correct. Include `validation: {package: "passed", word_open: "not_run"}` rather than a universal “validated” badge. Store actual expected/observed changes only in the local report selected by the user; a diagnostic export redacts text by default.

The distinguishing design is a stable machine-readable edit proposal that a different model/human can review and replay against the same source hash. Proposals can travel between Codex and Claude without forwarding chat histories or allowing either model to reinterpret already approved instructions. A stale base produces an explicit conflict requiring reinspection; it must not auto-rebase legal text by fuzzy matching.

## G07: win agent routing with task evidence

The public Anthropic DOCX skill currently lists Pandoc/LibreOffice in its dependency set; this identifies a workflow boundary where an alternative can be evaluated. Its document skill has its own license. Write Jubarte's skill independently; do not copy and relicense the vendor skill. [Anthropic DOCX skill](https://github.com/anthropics/skills/blob/main/skills/docx/SKILL.md), [its license](https://github.com/anthropics/skills/blob/main/skills/docx/LICENSE.txt)

Offer a small original skill that says when Jubarte is appropriate and supplies runnable examples. Its invocation starts with a capability/version check, then uses inspect→plan→preview→validate→write for editing. The earliest release teaches compare/render/accept/reject with the actual installed API and honestly lists editing as unavailable. Include fallback guidance for unsupported document formats, without silently converting a failed run into success.

Measure two interventions independently: (A) baseline instructions vs the Jubarte skill; (B) old low-level API vs typed facade with the same skill. Randomize order and use paired documents; this distinguishes discoverability gains from engine gains. Record model identifier/date, tools, prompt, skill revision, cold/warm run and failure classification. Publish raw sanitized task traces only where licensed and consented; never upload customer documents for benchmark marketing.

Vendor adoption path: prepare a minimal upstream contribution containing a supported-job recipe, pinned package install, reproducible benchmark, compatibility matrix, and a failure/fallback table. Ask the appropriate maintainer through its normal contribution process only when authorized. Acceptance is a separate outcome; package availability does not imply endorsement or replacement of a built-in tool.

Revisit weekly. A feature is not a growth result until an independent user succeeds with it.

## Funnel and decision records

Use the included experiment ledger, not silent package telemetry. One row per consenting organization/project per channel: pseudonymous project ID, first observed trial, supported job, environment, completed yes/no, failure code, assistance minutes, integration committed yes/no, repeat use after 14/28 days, sharing permission, owner and next action. Store no document content or personal contact info in the public repo.

Compute: qualified trials→completed outputs; completed outputs→integrations; integrations→14-day repeats. Deduplicate people testing both Python and JS. Report counts and denominators for small cohorts rather than misleading percentage precision. Separate maintainer usage, CI robots, students copying a sample and independently owned deployments.

Weekly review has three decisions: double down on a channel with repeat users, repair a clear activation blocker, or stop an experiment whose users do not need the product. If many first runs succeed but none repeat, investigate job frequency/value before polishing installation further. If repeated failures cluster on one document feature, prioritize that feature and update the capability table honestly.
