## Summary
This PR addresses a potential Regex Denial of Service (DoS) vulnerability in the `--regex` filter of the `read --for-edit` command by bounding the input length and explicitly configuring the regex compilation size limit.

## Evidence
- Before: `cargo run --bin jubarte --manifest-path Cargo.toml -- -V` after passing an unbounded string of 10M "a"s to `RegexBuilder::new().size_limit(10_000_000).build()` returns an error that it exceeds size limits, meaning unbound user input can hit compilation limits unexpectedly.
- After: The code explicitly bounds the input pattern to 1000 characters and sets the builder's `size_limit` to 1,000,000 to prevent algorithmic complexity attacks during the DFA construction phase. The test suites (`cli` and `read_for_edit`) pass without regression.

## Merge Danger
- **Door:** One-way (modifies CLI parameter handling bounds).
- **Blast Radius:** Low. Only impacts users attempting to supply excessively long (e.g. >1000 char) regex strings to `--regex`, which is effectively no one in legitimate use cases.

🚨 Severity: MEDIUM
💡 Vulnerability: The `--regex` flag previously passed unbounded user input directly to `regex::Regex::new()`.
🎯 Impact: While Rust's `regex` crate is mostly immune to backtracking DoS, unbounded regex compilation could exhaust memory or hit internal limits, potentially crashing the application unexpectedly.
🔧 Fix: Bounded input length to 1000 characters and used `RegexBuilder` with a 1MB `size_limit` to fail securely and prevent resource exhaustion.
✅ Verification: Both the CLI (`m7_cli`) and unit tests (`read_for_edit`) were run and pass successfully.
