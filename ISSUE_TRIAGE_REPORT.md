## How this was run

Pre-existing labels (`bug`, `ASAP`, `Future`, `md`, …) were never removed; nothing was commented, closed, or reopened. Builds/tests were not run (repo rule: no second Cargo process, no benchmark claims without gates) — every verdict is inspection-level.

## Label semantics used

- **done / pending** — `done` only when the *whole* ask demonstrably exists in the checkout: landed commit reachable from HEAD plus code, and a pinning test, CHANGELOG or docs reference. Partially implemented stays `pending`. Genuinely uncertain after checking → `pending`.
- **security** — the issue describes a vulnerability or security-relevant defect (data exposure/leak, world-readable files, injection, hostile-input resource exhaustion, validation bypass).
- **enhancement** — feature/perf/improvement request rather than a defect fix. (Count includes issues that already carried the repo's `enhancement` label.)
- **breaking-change** — implementing as requested would break documented behavior, public API, CLI flags, or output compatibility (also applied when an already-landed `done` fix is itself breaking per its issue).
- **complex** — spans multiple subsystems or needs architectural change; localized fixes are not complex.

## Notable clusters

- The **security tail is large**: 61 open security issues, concentrated in the bomb-review / dedup-security-plan families (#1611–#1640) — hostile-input hardening across admission, scrub, convert and validate.
- **done with security (13)** — hardened-input fixes already landed (e.g. #639 symlink refusal, #644 ZIP structural consistency, #1385 pilot-ledger permissions).
- **6 `done` fixes are breaking** (e.g. #1069, #1135, #1268) and **14 `done` were complex** — worth a passing mention in the next release notes.
